# AI 拍照助手 · 手机 App 落地方案

> 适用：AIAA4435 期末阶段（Week 8–13），3 人小组，已有 28 份问卷与完整交互设计。
> 目标不是发布级产品，而是**可运行的交互原型 + 可量化的 A/B/C 用户实验**。验收标准：能演示、能记录数据、能跑三种条件。

---

## 1. 技术栈：三选一

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **A. Web PWA**（getUserMedia + Canvas + MediaPipe/onnxruntime-web） | 最快出 demo（约 1 周）；免安装、免审核、双端通用 | iOS Safari 相机性能与权限限制；长时间运行发热 | 先出可演示原型的保底方案 |
| **B. Flutter**（推荐） | 一套代码 iOS/Android；热重载；`camera` + `google_mlkit_object_detection` 生态成熟 | 需要学 Dart（2–3 天可上手） | 课程交付主方案 |
| **C. 原生 Kotlin**（CameraX + ML Kit） | 性能最好、帧处理最自由 | 只有 Android；iOS 要重写 | 团队有人会 Android 时 |
| D. Unity + AR Foundation | 贴合 Week 4–6 教学；可接数字人 | 相机流/UI 比 App 框架重得多 | 只在期末想加 3D 讲师时用 |

**建议：B 为主，A 为备胎。** 如果到 Week 10 还没有可在手机上跑的东西，立刻切 A。

---

## 2. 架构：照抄你们 PPT 第 7 页

```
相机帧 ──► 感知层（本地 CV，帧不出设备）
              │  {scene, cues:[{type,value,confidence}]}
              ▼
         决策层（规则引擎：状态 + 冷却 + 置信度 + 静默）
              │  {action, text, confidence}
              ▼
         反馈层（AR 箭头 + ≤8 词一句话；长按展开解释 → 可选 LLM）
```

**关键约束**（与你们答辩口径一致，别破坏）：**帧永远本地处理**；发给 LLM 的只有结构化 JSON（无图片）；LLM 只负责"重述已批准的动作"，默认走本地模板。

---

## 3. 感知层：先做 4 个 cue 就够了

| cue | 做法 | 阈值建议 |
|---|---|---|
| `horizon_tilt` | 帧降到 320×240，Sobel + Hough 线检测地平线角度 | > 5° 提示"水平线歪了" |
| `subject_box` | ML Kit 目标检测取主体 bbox，判断是否落在三分点 | 偏移 > 1/6 画面宽 |
| `brightness` | Y 通道均值 + 高光溢出像素比例 | 溢出 > 15% 判过曝 |
| `glare` | 高光高亮 + 低饱和区域占比（问卷里发现的真实痛点） | 占比 > 8% 提示"镜头反光" |

每个 cue 输出 `{type, value, confidence}`，confidence 交给决策层用。

---

## 4. 决策层：状态机 + 规则表

- 状态：Idle / Intent / Guide / Capture / Review / Retry（对应 PPT 第 8 页）
- 每个状态只允许一组动作（如 Capture 里禁止一切新提示）
- 冷却 3 秒；同一 cue 5 秒内不重复；confidence < 0.6 静默；mute 全局生效
- 规则表写成数据（JSON/YAML），方便实验时调参，不用改代码

---

## 5. 反馈层

- AR 箭头/参考线（Canvas 叠加）+ 一句 ≤8 词的模板文案
- 长按 → 展开解释：调 LLM（DeepSeek），输入仅 JSON cues + 场景标签，超时 1.5 秒回退本地模板
- 可选 TTS（无障碍/运动场景）
- 拍后轻卡：1 个亮点 + 1 条建议，3 秒淡出

---

## 6. 四周排期（Week 8–11 出可演示版，Week 12 做实验）

| 周 | 交付 | 验收标准 |
|---|---|---|
| Week 8 | 骨架：相机预览 + 叠加层 + 埋点；跑通 `horizon_tilt` 一条 cue | 手机上能实时看到箭头 + 一句话 |
| Week 9 | 补齐 4 个 cue + 规则引擎 + 状态机 + mute | 四种提示都能触发，规则可调 |
| Week 10 | LLM 展开解释 + 模板兜底 + 完整埋点 + 2–3 台真机测试 | 断网/超时也不崩 |
| Week 11 | 小规模 pilot（3–5 人），修 bug，**冻结版本** | 无崩溃、日志完整 |
| Week 12 | A/B/C 对照实验 8–12 人（counterbalanced） | 数据可分析 |
| Week 13 | 分析与期末汇报 | 有结论、有图 |

**最小可行 Demo（第 1 优先级）**：只做 `horizon_tilt` 一条链路，端到端跑通。2–3 天完成，之后每个 cue 都是叠加。

---

## 7. 埋点：实验成败的关键

每次拍摄记录：时间戳、拍摄时长、当前条件(A/B/C)、触发的 cue、是否显示、是否被忽略、是否展开解释、是否重拍、照片 id。
没有这些日志，Week 12 的实验就只能靠问卷自评，说服力大打折扣。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 延迟/不稳定 | 默认模板；LLM 只做展开；1.5 秒超时回退 |
| CV 误报 | 置信度阈值 + 冷却 + 一键关 |
| iOS/Android 差异 | 先单平台跑通；必要时用 PWA |
| 演示当天翻车 | 录屏备份 + 一台备用手机 |
| 隐私承诺被破坏 | 帧不出设备；上传只有 JSON；日志脱敏 |

## 11. DeepSeek API 用法（你已有 key）

- Endpoint：`https://api.deepseek.com/chat/completions`，model `deepseek-chat`
- 请求体只含：场景标签 + cues 数组 + 当前动作；**不含图片**
- 提示词固定为"把动作改写成一句 ≤8 词的中文/英文提示，不要新增建议"
- 本地缓存：相同 cue+动作组合命中模板就不调 API，省延迟、省钱
- 记录 latency 与失败率，写进期末"技术方案"页

## 12. 第一周就能做的三件事

1. 用手机浏览器做一个 PWA 版（getUserMedia + 地平线检测 + 一句话提示），验证"实时提示"在真机上是否可行；
2. 把规则表（状态机 + 冷却 + 阈值）写成 JSON，明确每个参数的初值；
3. 设计埋点清单与实验流程（A/B/C 条件切换开关）。
