## P2-v9：实点稳定器 + 日志系统

### 一、实点为什么抖，以及怎么根治

之前实点公式是 `实点 = 0.5 + (主体位置 - 目标位置)`。
**框抖 1%，实点就抖 1%**，而且被引导线在视觉上放大。

**为什么不用低通滤波**：滤波会让用户真的移动手机时也变迟钝，而且小幅抖动依然会缓慢渗透。

**实际用的方案：滞后带（hysteresis）**

关键洞察 —— **三分法本身就是一个宽容的构图**。主体不必精确落在 1/3 处，落在 1/3 附近一片区域里都算好构图。所以：

| 情况 | 行为 |
|---|---|
| 主体偏移 **< 4.5%**（带内） | **实点纹丝不动** ← 消除抖动的关键 |
| 主体偏移 **> 4.5%**（带外） | 需连续 **2 帧**同向确认，才更新实点 |
| 更新之后 | 主体重新获得整个带宽的余量 |

效果对比（单测实测）：

| | 40 帧抖动输入下的实点累计位移 |
|---|---|
| 无稳定器 | 明显（每帧都在动） |
| 有稳定器 | **0（完全不动）** |

同时用户真的移动手机时，实点在 2 帧（约 0.2 秒）内跟上，不会迟钝。

### 二、日志系统

`AppLog` 三层设计：

| 层次 | 说明 |
|---|---|
| 内存环形缓冲 | 最近 2000 条，随时可读，不阻塞 |
| 文件持久化 | `files/logs/session-<时间>.log`，App 被杀也在 |
| 导出 | 复制到剪贴板 / 分享为文件 |

**怎么看日志**：**长按左上角 HUD** 打开日志查看器。

查看器功能：
- 按关键字过滤（`Anchor` / `Stream` / `Pick` / `Error`）
- 「复制」把日志放进剪贴板
- 「分享」把日志文件发出去（微信、邮件都行）

**记了哪些关键事件**：

| Tag | 内容 |
|---|---|
| `App` | 启动、版本号 |
| `Stream` | 每 30 帧记录：帧号、检测到几个、耗时、框中心/尺寸 |
| `Anchor` | **实点每次更新**：主体位置、实点位置、本帧抖动、累计更新次数 |
| `Lock` | 自动锁定事件 |
| `Pick` | 点击锁定事件（含没找到物体的记录） |
| `Detector` | ML Kit 异常（之前是静默吞掉的） |

导出后用记事本打开就能看。遇到问题可以直接把日志发过来。

## P2-v8：修一个致命 bug（框和实点完全不出）（已被 P2-v9 取代）

### 症状

v7 装上后**框和实点完全不显示**，点屏幕也没反应。

### 根因：`closeOnce` 用了成员变量

```kotlin
// v7 的错误写法
private val closed = AtomicBoolean(false)      // ← 整个分析器共用一个！

private fun closeOnce(image: ImageProxy) {
    if (closed.compareAndSet(false, true)) {   // ← 第一帧就把它设成 true
        image.close()
    }
}
```

**第一帧**处理完 → `closed` 变 `true` → **此后所有帧都不会被 `image.close()` 关闭**。

后果是致命的：`ImageProxy` 不关闭，CameraX 的 `ImageAnalysis` 就永远不会再交付新帧。所以：

| 现象 | 原因 |
|---|---|
| 框和实点不出现 | 检测器只跑了**第一帧**，之后彻底饿死 |
| 点屏幕没反应 | 没有新帧，`pickAt` 永远等不到输入 |
| HUD 数值也不更新 | 整个分析管线卡死 |

这是我上一版引入的死锁——把原来的 `finally { image.close() }` 改成回调式关闭时，把「每帧一个标志」写成了「全局一个标志」。

**修复**：用 `WeakHashMap<ImageProxy, AtomicBoolean>` 给每帧独立的关闭标志。用 WeakHashMap 是为了不泄漏已经释放的 ImageProxy。

### 新增：自动锁定按钮

底部新增 **「自动锁定」** 按钮，一键把当前检测到的主体锁住并显示框 / 实点。

用途：
- **测试**：确认检测链路是通的
- **兜底**：不想点屏幕时的一键锁定
- 之后用户点屏幕仍然听用户的（会覆盖自动锁定）

### 新增：HUD 诊断信息

HUD 的主体行现在会显示：

```
主体 帧#127 1个 34ms 锁定
```

| 字段 | 含义 |
|---|---|
| `帧#127` | **累计回调帧数**。不涨 = 检测根本没跑（这次的 bug 就是它不涨） |
| `1个` | 本帧检测到几个主体 |
| `34ms` | 单帧耗时 |
| `锁定` | 是否处于手动锁定 |
| `错误: ...` | 检测失败时的异常类名和消息（之前是静默的） |

以后遇到"没反应"，先看这行的帧数涨不涨。

## P2-v7：方案 A —— 拆成两个检测器（有致命 bug，见 P2-v8）

### 问题定位（基于官方文档）

v6 的框抖、锁不住，根源是用错了 ML Kit 的检测模式。[官方文档](https://developers.google.cn/ml-kit/vision/object-detection/android?hl=zh-cn) 写得很清楚：

> `STREAM_MODE`：低延迟，但在**最初几次调用**时可能返回不完整结果；会分配跟踪 ID。

> 该 API 针对两个核心场景优化：
> 1. **实时检测并跟踪取景器中最突出的对象**
> 2. **检测静态图片中的多个对象**

也就是说：**实时场景官方做法是单目标**，多目标是静态图片的做法。v6 两个都开了 `enableMultipleObjects`，结果每帧在最多 5 个对象之间重新分配 trackingId —— 框乱跳、锁不住、其他物体干扰全是这个引起的。

另外我引入的 `enableClassification()` 也是纯负担：文档说它只分五个粗类（时尚商品/食品/家居用品/地点/植物），对本项目没用，还增加耗时。

### 方案 A：两个实例各司其职

| 实例 | 模式 | 用途 | 频率 |
|---|---|---|---|
| `streamDetector` | `STREAM_MODE` + **单目标**（不调 enableMultipleObjects） | 实时跟踪最突出主体 | ~10fps，限流 |
| `pickDetector` | `SINGLE_IMAGE_MODE` + 多目标 | 只在点击时跑一次，找出"点的是哪个" | 按需 |

这样同时满足：官方推荐的实时用法 + "点哪个锁哪个"的交互。

### 顺带修的两个真 bug

**bug 1：ImageProxy 提前关闭。** 之前把帧交给 ML Kit 后立刻 `image.close()`，但 `InputImage.fromMediaImage()` 是**直接操作 media.Image**（官方明确说这种方式不复制、最省），ML Kit 异步处理时会读到已释放的 buffer。

现在改成**回调式关闭**：ML Kit 处理完 → `onDone()` → 才 close。加 `AtomicBoolean` 防重复关闭。

**bug 2：手动锁定被实时流覆盖。** 我第一版写 `if (manualLock) { list.firstOrNull() } else { list.firstOrNull() }` —— 两个分支一模一样，用户点了锁定，下一帧就被检测器"最突出"的结果顶掉。

现在加了跟丢判定：实时流的物体必须跟锁定框**基本重合**（中心距离 < 0.18 且面积比在 0.45~2.2）才更新，否则视为跟丢，保持锁定框不动。

### 交互不变

| 操作 | 效果 |
|---|---|
| **点屏幕** | 对焦 + 用静态图检测锁定该处物体（**优先于**自动锁定） |
| **「自动锁定」按钮** | 一键锁定当前最突出的主体 |
| **长按 HUD** | 退出手动锁定，回到自动跟随 |
| **移动手机** | 让白十字压到黄靶心 → 按快门 |

HUD 主体行是诊断入口：`主体 帧#127 1个 34ms 锁定`，帧数不涨说明检测没跑。

### 仍然存在的限制

1. **单目标模式下"最突出"由 ML Kit 决定**，未必是用户想要的。所以点击锁定仍是必要的补充。
2. **实点仍可能小幅抖动** —— 方案 A 降低了框抖动的源头，但没有加时间滤波。如果还抖，上方案 B（One-Euro 滤波）。
3. 点击后需要等一帧（约 100ms）才出结果，是异步的。

## P2-v6：锁定主体 + 构图建议 → 实点（已被 P2-v7 取代）

### 重新理清的概念（之前搞错过）

v5 把主次搞反了。正确的分工是：

| 谁 | 做什么 |
|---|---|
| **后台** | 锁定主体 → 框定范围 → 算构图建议 → 吐出**实点位置** |
| **前台** | 点屏幕锁主体 → 把**虚点挪到实点** → 点快门 |

**关键定义**：

| 元素 | 是什么 |
|---|---|
| **主体框** | 锁定中的那一个物体（**只画这一个**，其他候选一律不显示） |
| **实点（黄靶心）** | **镜头中心应该到达的位置**，由构图建议算出 |
| **虚点（白十字）** | **镜头中心**，固定在屏幕正中，不会动 |

所以用户唯一要做的动作是：**移动手机，让白十字压到黄靶心，然后按快门。**

### 构图建议怎么算

输入：锁定主体的框。输出：实点位置。

```
1. 选三分点：主体中心离哪个三分交点最近，目标就是它
2. 留白修正：主体朝向已知时，让它落在"前方有空间"的那条三分线上
3. 反推实点：实点 = 0.5 + (主体当前位置 - 目标位置)
4. 夹住边距：实点不能贴边（留 8%），否则用户挪不过去
```

第 3 步的符号最容易搞反，这里写清楚：

> **镜头往右移 → 画面里所有东西往左移。**
> 主体现在在 0.80，想让它到 0.667，就得左移 0.133。
> 那镜头就要往**右**移 0.133 → 实点 = 0.5 + 0.133 = 0.633 ✓

这个方向有单测专门锁着（`CompositionAdvisorTest`），因为搞反的话用户会越拍越歪。

### 只留一个框

v5 把 ML Kit 找到的所有物体都画了框，观感很差，而且用户也不关心别的。现在：

- **只画锁定主体的框**，且**只画四个角**（不是整圈虚线）—— 干净，不遮挡本体
- 其他候选一律不渲染
- 构图达标时，框角变青绿

### 前台的三个动作

| 操作 | 效果 |
|---|---|
| **点屏幕** | 对焦 + **立即锁定**该处的物体（再点别处就换主体） |
| **长按 HUD** | 解除锁定，回到自动模式（自动选最可能的主体） |
| **移动手机** | 让白十字压到黄靶心，压住后两者都变青绿 → 按快门 |

没有识别到主体时：**只显示镜头中心**，不显示实点、不弹提示 —— 画面干净，不打扰。

底部有一句话提示（如"手机往右""手机往下"），达标时变成"构图可以，直接拍"。

### 诚实的限制

1. **ML Kit 默认模型是粗分类**，远景小主体、低对比度主体识别率不高。
2. **实点是基于主体当前框算的**。主体框本身在抖（ML Kit 每帧框略有不同），所以实点会有小幅跳动。已限制检测到 ~5fps 来缓解，但如果实点抖动明显，需要加时间平滑。
3. **留白规则目前没有真正的"朝向"信息** —— ML Kit 不提供人物朝向。代码里预留了 `facingRight` 参数，暂时传 null（不强行改三分线）。要做真正的朝向判断得接人脸关键点或姿态估计。

## P2-v5：先找主体，再谈构图（已被 P2-v6 取代）

### 为什么放弃"检测线"

v4 把检测到的线画了出来，想法是"让用户看到算法在算什么"。但这个方案本身就不成立：

1. **用户不关心那条边。** 他关心的是"我要拍的东西摆得对不对"。
2. **算法选边的依据是错的。** 逐列找**对比度最高**的那条边，跟"画面里的主体在哪"没有必然关系。桌沿可能比远处地平线对比度高得多，于是算法锁到桌沿 —— 用户可以看见这一点了，但看见也没用，他改变不了算法选哪条边。

**结论：问题出在最上游。** 先确定主体，才谈得上构图；边检测只能在知道主体之后，用来服务于构图，而不是反过来。

### 现在怎么做

**第一步：找主体。** 用 ML Kit Object Detection（`STREAM_MODE` + `enableMultipleObjects`）。

`STREAM_MODE` 的关键价值是返回 `trackingId` —— 同一个物体跨帧 ID 不变。没有这个就没法做"锁定"，框会一直跳。

**第二步：选主体。** 一帧里可能有多个候选，按优先级选（`SubjectSelector`）：

| 优先级 | 规则 | 为什么 |
|---|---|---|
| 1 | **用户点击处附近的主体** | 用户意图最高优先。点屏幕 = 我要拍这个 |
| 2 | **已锁定的 trackingId** | 跟住不变，框才不会乱跳 |
| 3 | **离画面中心最近**（面积加权） | 默认情况下主体通常在画面中 |
| — | 面积 < 1.5% 或 > 95% 的框忽略 | 前者是噪点，后者是整屏误判 |

**第三步：给实点。** 在**三分法交点**画一个固定靶心（空心底座 + 十字），用户把主体挪到它上面。

实点位置**跟着主体走但方向相反**：主体在左 → 实点放右三分线（给主体前方留空间）；主体在右 → 放左三分线。这符合经典构图的空间留白规则。

### 交互

| 操作 | 效果 |
|---|---|
| **点屏幕** | 对焦 + **锁定点击处的主体**（同时优先选它） |
| **长按屏幕** | AE/AF 锁定（原有功能） |
| **长按 HUD** | 开关主体框显示（实点始终保留） |
| 主体框变青绿 + 四角加粗 | 当前锁定目标 |
| 实点变青绿 + 外圈 | 主体中心已落到实点上 |

**没有识别到主体时**：实点照常显示在三分交点，不弹任何提示 —— 退化成纯构图辅助，不打断拍摄。

### 一个诚实的说明

ML Kit 的默认模型是**粗分类**（对物体大类做检测），不是"人物/人脸"专用检测器。所以：

- 它能框出桌子、人、椅子、显示器等常见物体；
- 但**对远景的小主体、低对比度主体、纯色墙面上的东西识别率不高**；
- `label` 字段经常为空，这是模型本身的性质，不是 bug。

要更高精度得换成专用模型（如 MediaPipe / 自训练 TFLite），那是后续可选工作。

### APK 变大了：6 MB → 27.5 MB

ML Kit 的 native 库每个 ABI 约 6~12 MB，四个 ABI 全打进去是 **52 MB**。已在 `build.gradle.kts` 里限制为 `arm64-v8a` + `armeabi-v7a`（去掉仅模拟器用的 x86/x86_64），降到 27.5 MB。

用 bundled 版本而不是 play-services 版本，是为了**离线可用** —— 不需要首次联网下载模型。代价就是这 20 多 MB。

## P2-v4：把检测到的线画出来（已废弃，见 P2-v5）

### 为什么要做这个

前面几版里，用户看到的只是一个数字（`水平 +2.3°`）。但这个数字是从画面里**哪条边**算出来的，用户完全不知道。

实际拍摄时画面里往往同时有好几条边：桌沿、窗框、远处地平线、天花线。算法的做法是"逐列找最强的那条边"，所以它到底锁到了哪条边，完全取决于纹理对比度 —— 可能锁到你没在看的那个。**数字再准，锁错边就是误导。**

所以这一步不是加功能，是**让前面的工作变得可验证**：把算法实际拟合出来的那条线段画在画面上，位置和角度都来自真实的拟合结果（`lineYRatio` / `lineXRatio` + 角度）。

### 界面上看到的

| 元素 | 颜色 | 含义 |
|---|---|---|
| **水平检测线**（黄色虚线 + 两端圆点） | 暖黄 | 算法认定的那条水平边，贴在它真实的位置上 |
| **竖直检测线**（蓝色虚线） | 冷蓝 | 算法认定的那条竖直边 |
| **变青绿** | 青绿 | 这条线已对齐（≤1°） |
| **线条上的小标签** | — | `水平 +2.3°` / `竖 -0.8°`，就近标注 |

**操作**：长按左上角 HUD 可开关检测线显示。

### 校准后画哪条线

检测线画的是**扣掉镜头装配偏差之后**的角度（`horizonAngle - sensorOffsetDeg`），所以校准之后：
- 检测线水平 = 手机框正 = 水平仪读数 0°
- 两者可以互相印证

如果校准后发现"检测线画得正、但水平仪不为 0"，说明校准数据有问题，重量一次校准即可。

### 已知取舍

检测线反映的是**算法认到的那条边**，不是"画面的真实水平"。这两者在场景里有明显水平结构时一致，在纯色/弱纹理场景下不一致（此时置信度低，线会消失）。这是有意为之 —— 线消失告诉用户"这里靠不住了"，比画一条假的线诚实。

## P2-v3：改用手机自己的水平仪 + 靶心校准

### 为什么放弃 P2-b 的方案

P2-b 画了两条固定基准线，想让用户"把画面里的线跟基准线对齐"。实测行不通，原因有两个，而且都不是调参能解决的：

1. **画面上两条线并不能定义 0°。** 基准线固定在屏幕正中，它只说明"屏幕中心在哪"，不说明"手机歪了多少"。用户没法从它读出偏移量。
2. **相机模组有装配偏差。** 画面里"看起来正"的水平线，和手机框真正水平，差 1~3° 是常态。这不是算法误差，是硬件物理偏差 —— 所以画面检测永远对不上手机水平仪。

**结论：判定"正不正"必须用重力传感器**，它不依赖画面内容（白墙、天空、纯色地板下画面检测直接失效），也不受装配偏差影响。

### 新方案：一个靶心 + 一次校准

| 元素 | 说明 |
|---|---|
| **靶心（白色空心双圈 + 十字）** | 固定的目标点，代表"手机框正"的位置 |
| **当前点（黄色实心圆）** | 跟着重力传感器实时移动，表示手机现在歪多少 |
| **引导线** | 从黄点指向靶心，告诉你往哪边转 |
| **青绿 + 外圈** | 已压住（≤0.6°），可以点"完成校准"了 |

操作流程：

1. 点底部 **"校准水平"** → 进入校准模式；
2. 举着手机找一条**远处明显的水平线**（地平线、远处楼顶、桌子边缘都行）；
3. 转动手机，让**画面里的水平线**经过靶心，同时**黄点压住靶心**；
4. 黄点和靶心都变青绿、提示"已对齐" → 点 **"完成校准"**。

校准存下两个值：

| 存什么 | 含义 | 解决什么 |
|---|---|---|
| `zeroRoll` | 那一刻重力传感器的 roll 读数 | 传感器基准误差 |
| `sensorOffsetDeg` | 那一刻画面检测到的水平线角度 | 相机模组装配偏差 |

之后 HUD 里 `水平仪` 那一行就是**扣掉零位后的真实倾斜**，`画面线` 是扣掉装配偏差后的修正值。

### 数值跳动的第二个根因也修了

P2-b 的 EMA 有个问题：**坏值是等权掺进来的**。只要有一帧检测偏了 3°，估计就被拉走一截，要十几帧才慢慢回来 —— 表现就是"每隔一两秒跳一下"。压低 alpha 确实能稳住，但转动时又跟不上了。

P2-c 换成**鲁棒重加权平均**（`RobustSmoother`）：

```
w = 1 / (1 + (误差 / 2°)²)        ← Cauchy 权重
估计 ← 估计 + 0.25 × 误差 × w
```

误差小的时候 w≈1（跟手不迟钝），误差大的时候 w≈0（坏值推不动）。另外加了"连续 8 帧都偏离 → 认定是用户真在转，直接跟上"的逃逸机制，不会卡死。

单测锁住了这个行为（`RobustSmootherTest`）：单帧偏 6°，估计移动 **< 0.2°**；用户真转 8°，20 帧内跟上。

### 一个诚实的限制

`TYPE_GRAVITY` 依赖手机内部的陀螺仪融合。**拍平面（俯拍）时 roll 会退化**——重力几乎全部落在 z 轴上，x/y 分量接近 0，此时 atan2 的输入过小，读数是数学上的病态。所以这套水平仪**只对竖持拍摄有效**，俯拍不受支持。这是物理限制，不是实现问题。

## P2-v2：数值稳了，也有基准线了（已被 P2-v3 取代）

### 问题 1：数值一秒跳 4–5 次

**原因**：逐帧检测本身抖动很大（边缘检测对光照、纹理、手持微动都很敏感），每帧结果差个几度是常态。直接把原始值显示出来当然会疯跳。

**解决：三级滤波**（`FrameAnalyzer` 里）

| 机制 | 参数 | 作用 |
|---|---|---|
| **置信度门槛** | `conf < 0.25` 不喂新值 | 检测失败时不跳到 0，沿用上一次结果 |
| **指数移动平均** | `α = 0.15` | 大约 0.2 秒的响应时间，过渡平滑不滞后 |
| **死区** | 变化 < 0.4° 不更新输出 | 读数不会在 0.1° 级别来回跳 |

同时把 UI 刷新从 **8Hz 降到 4Hz**（250ms），看着更稳。

想调手感的话改这几个常量（`FrameAnalyzer.kt` 顶部）：

```kotlin
private val emaAlpha = 0.15f      // 越小越稳，但跟手变慢（0.1~0.3 之间调）
private val deadbandDeg = 0.4f    // 死区，越大越稳但越"钝"
var emitIntervalMs: Long = 250    // UI 刷新间隔
```

### 问题 2：没有基准线，不知道 0° 在哪

新增 `BaselineOverlay`：画面上固定画两条参照线。

| 元素 | 位置 | 含义 |
|---|---|---|
| **水平基准线**（白色虚线） | 画面正中 | 这一行就是 0°，让画面里的水平线跟它平行 |
| **竖直基准线**（白色虚线） | 画面正中 | 这一列就是 0°，让建筑立柱跟它平行 |
| **中心圆环 + 十字** | 正中交点 | 构图中心参考 |

**颜色即状态**：

| 颜色 | 含义 |
|---|---|
| 灰（半透明白） | 没检测到线（画面里没有明显的水平/竖直边） |
| 白（实心亮） | 检测到，但还没对齐 |
| **青绿** | **已对齐**（角度 ≤ 1°） |

HUD 里也会标 `✓`：

```
水平 -0.4°  ✓        ← 对齐了
竖线  2.1°           ← 还有点歪
亮度 128  暗 12%  亮 3%
  4ms  320×240  rot90
```

### 怎么验证

1. 把手机**放平在桌面上**，看水平基准线是否变绿、HUD 是否 `✓`；
2. 对着**门框/窗框的竖边**，转手机让竖线对齐，看竖直基准线变绿；
3. 快速转动手机 → 数值平滑跟随，停止后**稳定不跳**；
4. 用手遮住镜头 → 两条线变灰（检测不到），数值保持上一次（不会瞬间归零）。

## P2-a：管线和算法都通了

### 做了什么

1. **接入 `ImageAnalysis`**：CameraX 逐帧回调，`STRATEGY_KEEP_ONLY_LATEST` 保证不积压
2. **移植几何检测到 Kotlin**（`detect/Geometry.kt`，对应之前的 `detect.js`）：
   - `estimateHorizon` —— 逐列找水平边 → 加权最小二乘 → 内点筛选
   - `detectVerticals` —— 同上转置，抓建筑透视
   - `measureBrightness` —— 均值/暗部/高光溢出
3. **帧提取优化**：从 `ImageProxy` 的 Y 平面直接取灰度（YUV 的 Y 就是亮度，**不用转 RGB**），
   一次性 `buffer.get(ByteArray)` 后按 `rowStride/pixelStride` 采样，降到 320×240
4. **旋转处理**：`rotationDegrees==90/270` 时把"水平/竖线"结果对调（竖屏下传感器方向是横的）
5. **实时 HUD**：预览区左上角显示检测数据，点击可隐藏

### 怎么看 HUD

```
水平 -2.3°  conf 0.62      ← 地平线角度 / 置信度
竖线  1.1°  conf 0.48      ← 建筑竖线偏离角度
亮度 128  暗 12%  亮 3%     ← 明暗统计
  3ms  320×240  rot90      ← 单帧耗时 / 分析分辨率 / 旋转角
```

**验收标准**：
- 转动手机 → "水平"角度跟着变，转正后接近 0；
- 对着建筑竖边 → "竖线"角度变化；
- 用手遮住镜头 → "亮度"掉到很低、"暗"占比升高；
- 对着强光 → "亮"占比升高；
- 单帧耗时（`3ms` 那种）应该 < 15ms，超过说明设备较慢，可再降分辨率。

## v3 改了什么：画面与控件不再重叠

**问题**：v2 的预览是全屏，底部控制面板用半透明黑盖在画面上，导致画面下 1/3 被遮住——构图时看不到主体底部在画面里的位置。

**解决**：改成上下分区，两者互不遮挡。

```
┌─────────────────────────────┐
│ [⚡自动]              [▦]    │ ← 顶部薄工具条（半透明胶囊，只占 ~50dp）
│                             │
│                             │
│         取景画面              │ ← 预览区：LinearLayout weight=1
│       （三分线 / 对焦框）      │    占满顶部到控制面板之间的全部空间
│                             │
│                             │
├─────────────────────────────┤ ← 这里开始是独立面板，不透明
│  ☀ ───────●────── +0        │
│      [1x]  [2x]  [8x]       │   控制面板：背景 #0B0F14（实色）
│                             │
│  [缩略图]   ( ◉ )   [⟳]     │
└─────────────────────────────┘
```

关键改动：

| 改动 | 说明 |
|---|---|
| 根布局 | `FrameLayout` → `LinearLayout(vertical)` |
| 预览区 | `weight=1`，占满剩余高度（约 2/3） |
| 控制面板 | `wrap_content`，实色背景，不盖在画面上 |
| 闪光快门遮罩 | 只覆盖预览区，不再闪整个屏幕 |
| 顶部工具 | 缩成薄胶囊（闪光 + 网格），贴合主流相机外观 |
| 画面填充 | `app:scaleType="fillCenter"`，避免黑边 |

控制面板高度约 200–220dp，在常见手机上正好是"画面 2/3、控件 1/3"的比例。想再调的话改 `controlPanel` 的 padding 和各行 `layout_marginTop` 即可。

### 对焦：加了真实结果反馈（这是"没感觉"的关键）

之前的问题：界面上看不出对焦到底成没成。现在用 **`FocusMeteringAction` 返回的 future**：

```kotlin
val future = cam.cameraControl.startFocusAndMetering(action)
future.addListener({
    val success = future.get().isFocusSuccessful      // ← 真实结果
    binding.focusRing.setFocusResult(success)
}, ContextCompat.getMainExecutor(this))
```

对焦框有四种状态：

| 状态 | 外观 | 触发 |
|---|---|---|
| 对焦中 | 白灰**虚线**角框 + "对焦中" | 点击瞬间 |
| 已合焦 | **青绿实线** + 轻微回弹 + "已合焦" | 对焦成功 |
| 对焦失败 | **红色虚线** + "对焦失败" | 对焦超时/失败 |
| AE/AF 锁定 | **琥珀实线** + "AE/AF 已锁定" | **长按屏幕** |

**长按锁定**是让"对焦有效果"最明显的手段：锁住之后，你移动手机构图时焦距和曝光都不会乱跳，这就是专业相机的做法（[iPhone 的 AE/AF Lock](https://www.engadget.com/2014-04-09-iphone-101-how-to-lock-exposure-and-focus-in-the-camera-app.html) 同理）。

另外修了一个常见坑：**每次对焦前先 `cancelFocusAndMetering()`**，否则部分机型上连续点击不生效（[CameraX not focusing on tap](https://stackoverflow.com/questions/79981153/android-camerax-not-focusing-on-tap)）。

### 为什么"对焦看不出变化"

如果手机景深大（常见于广角 + 远景），对焦一直在连续追焦，点一下本来就看不出差异。**验证方法**：

1. 把手指/纸片放在镜头前 10–20cm，点它 → 画面应变清晰，后面的背景变虚；
2. 长按锁定后再移动手机 → 焦距被锁住，不会自己追焦。

如果这两条都没反应，说明这台机器的 `startFocusAndMetering` 有问题，告诉我具体机型我再看。

val action = FocusMeteringAction.Builder(
    point,
    FocusMeteringAction.FLAG_AF or FocusMeteringAction.FLAG_AE   // 对焦 + 测光

scaleDetector = ScaleGestureDetector(this, object : SimpleOnScaleGestureListener() {

## 已知限制

- 只做了 Android；iOS 需要 AVFoundation 另写
- 竖屏锁定（`screenOrientation="portrait"`）

- **点击锁定是异步的**：点完要等一帧（~100ms）才出结果
